# 엘리스 GPU 설명 생성 실행 및 검증

2026-11-23, `perf/elice-gpu-20261123`. SMTP 통합 브랜치의 `ae7b4b2` 위에 추가한 GPU 실행 도구입니다. 프런트엔드와 기존 설명 검증 코드를 변경하지 않습니다.

## 실제 측정 환경

- 엘리스 G-NAHPM-10: NVIDIA A100 80GB PCIe의 **MIG 1g.10gb 한 조각**, CUDA에서 보이는 메모리 9,728 MiB. 전체 80GB를 사용한 결과가 아닙니다.
- CPU 2 vCore, RAM 24 GiB, Ubuntu 22.04 / glibc 2.35, 호스트 NVIDIA 드라이버 535.247.01.
- llama.cpp 공식 `b12640` CUDA 12.8 빌드, 커밋 `56eea9e4b`. CPU와 GPU 모두 같은 실행 파일을 사용합니다.
- Qwen3.5-4B Q4_K_M, SHA-256 `217002fa8008ef4fc6d548353a3aebef055a96e6ff8e0e2c0953ef8254a89c14`.
- 토크나이저 리비전 `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`, 프롬프트 `v1.3-explanation-7`.
- 로컬 PC에서 측정한 성능 수치는 포함하지 않습니다.

## 동일 조건의 실제 설명 처리 결과

기업 등록 자료에서 미리 고정한 처방 후보 3개를 각 모드에서 한 번씩 처리했습니다. 각 후보는 원본 관계 대조 후 **생성 → 인용 원문 일치 검사 → 별도 검토 요청 → 검토 결과 검사**를 모두 통과해야 성공입니다.

| 후보 ID | CPU 생성+검토 | GPU 생성+검토 | 결과 |
| --- | ---: | ---: | --- |
| 17693 | 303.513초 | 72.887초 | 양쪽 READY |
| 8355 | 272.138초 | 12.753초 | 양쪽 READY |
| 7415 | 308.073초 | 12.664초 | 양쪽 READY |
| 중앙값 | **303.513초** | **12.753초** | **약 23.80배 / 95.80% 단축** |
| 3개 순차 처리 합계 | **883.724초** | **98.304초** | **약 8.99배 / 88.88% 단축** |

첫 GPU 요청에는 입력 형태에 따른 추가 GPU 코드 준비가 포함됐습니다. 첫 요청의 72.887초를 제외하거나 실패로 처리하지 않았습니다. 이후 두 후보의 약 12.7초와 구분해야 합니다. 실제 토큰 생성 처리량은 CPU 약 3.4 token/s, GPU 약 35.8~35.9 token/s였습니다.

정식 비교와 별도로 다른 작업이 없는 상태에서 새 GPU 코드 캐시 폴더를 만들어 초기 준비도 확인했습니다. 모델 파일은 OS 캐시에 남아 있는 조건이며, **모델 준비 54.672초 + 첫 번째 검증된 설명 72.149초 = 약 126.8초**였습니다. 이 진단의 설명도 필수 검사 PASS 및 READY입니다. 준비 중 다른 컴파일 작업과 겹쳐 관찰했던 약 106초는 정식 초기 준비 성능값으로 사용하지 않습니다. 사용자 요청마다 새 모델 프로세스를 띄우기보다 상주 서버를 유지해야 합니다.

초기에는 후보당 2회 반복을 계획했으나 CPU 2 vCore에서 한 건에 약 5분이 걸리는 것이 확인돼, 두 번째 반복을 시작하기 전에 모든 사전 지정 후보의 첫 번째 실행만 보존하도록 조정했습니다. 실패 결과를 골라 제외하거나 재시도한 결과가 아닙니다. 세 후보씩인 소규모 측정이며 일반적인 p95·동시 접속 성능을 나타내지 않습니다.

## 유지한 검증과 측정 범위

- CPU `--device none --n-gpu-layers 0`, GPU `--n-gpu-layers 999`; GPU 로그에서 **33/33 레이어 offload** 확인.
- 두 모드 모두 CPU 스레드 2, batch/ubatch 512, 컨텍스트 4096, 슬롯 1, temperature 0, seed 42.
- 입력 한도 3072, 출력 한도 1024, 모델 호출별 타임아웃 180초 유지. 생성과 검토가 별도 호출이므로 후보 전체 시간은 180초를 넘을 수 있습니다.
- 매 후보마다 애플리케이션의 완성 결과 캐시를 지웠습니다. 서버의 `cache_prompt=true` 설정은 양쪽에서 유지했습니다. 캐시 적중 결과는 위 속도 비교에 포함하지 않습니다.
- 후보마다 필수 원본 관계 검사 6개를 확인하고, 생성/인용/검토 검사를 그대로 수행했습니다. 6개 실행 모두 필수 검사 PASS 및 READY.
- 원본·벡터 정합성을 확인한 기업 자료와 기존 검색 결과에서 환자 서술 없이 등록 증상 표현·기업 후보·근거만 추출했습니다. 인스턴스에서 동일한 `verify_candidate` 함수로 고정 스냅샷을 재검사했고 파일 해시도 대조했습니다. 기업 원문 스냅샷과 모델 파일은 Git에 추가하지 않습니다.
- 인스턴스에서 기존 설명·캐시·취소·출력 중단 관련 회귀 테스트 **15개 통과**.
- 측정 구간은 모델이 준비된 상태의 **설명 생성과 검토 단계**입니다. DB 조회, E5 검색, 사용자 인증 및 화면 렌더링을 포함한 전체 서비스 응답 시간이나 독립 문맥 분류·임상 정확도 평가가 아닙니다.

## 확인한 실행 문제와 해결

1. 공식 Ubuntu 실행 파일이 요구하는 `GLIBC_2.38` / `GLIBCXX_3.4.32`가 인스턴스 기본 라이브러리에 없었습니다.
2. CUDA 12.8 배포 파일의 PTX를 호스트 드라이버 535에서 준비할 때 `a PTX JIT compilation failed` 오류가 발생했습니다. GPU 목록에 장치가 보이는 것만으로 실제 모델 실행이 보장되지는 않았습니다.
3. Ubuntu 호환 라이브러리와 NVIDIA `cuda-compat-12-8` 570.211.01을 **전용 폴더에만 추출**하고, 해당 모델 프로세스에만 경로를 적용했습니다. 시스템 드라이버, 시스템 패키지와 팀 서비스 파일은 변경하지 않습니다. [NVIDIA 공식 호환성 설명](https://docs.nvidia.com/deploy/cuda-compatibility/latest/forward-compatibility.html)
4. 깨끗한 Python 환경에서 채팅 템플릿 실행에 필요한 Jinja2가 빠져 있었습니다. 검증에 사용한 토크나이저·템플릿 패키지를 `backend/requirements-local-model.txt`에 명시했습니다. PyTorch는 GGUF 실행에 사용하지 않습니다.

## 재현 및 서비스 연결

아래 작업은 위 사양의 엘리스 Linux 인스턴스에서 수행합니다. 준비 스크립트는 GPU 유형과 드라이버 계열을 확인하고, 파일 SHA-256이 다르면 중단합니다. 새 버전으로 자동 대체하지 않습니다.

```bash
python3 backend/scripts/elice_gpu_prepare.py
python3 -m venv ~/codex-bench-20261123/venv
~/codex-bench-20261123/venv/bin/python -m pip install -r backend/requirements-local-model.txt
~/codex-bench-20261123/venv/bin/python backend/scripts/elice_gpu_server.py --port 18091
```

기본 전용 폴더는 `/home/elicer/codex-bench-20261123`입니다. 서버는 `127.0.0.1`에만 바인딩하고 비공개 API 키 파일을 사용합니다. 사용 중인 포트는 빼앗지 않고 중단합니다. 준비 스크립트는 CLI fallback용 `llama-completion-gpu` 래퍼도 생성합니다.

같은 인스턴스에서 실행할 팀 백엔드에는 다음 항목을 기존 비공개 설정과 합쳐야 합니다. 실제 API 키는 Git이나 채팅에 쓰지 않고 `benchmark-api-key.txt` 또는 별도로 지정한 비공개 키 파일에서 읽습니다.

```dotenv
KM_CDSS_LLAMA_SERVER_URL=http://127.0.0.1:18091
KM_CDSS_LLAMA_SERVER_API_KEY=키_파일과_동일한_비공개_값
KM_CDSS_LLAMA_EXECUTABLE=/home/elicer/codex-bench-20261123/llama-completion-gpu
KM_CDSS_EXPLANATION_MODEL=/home/elicer/codex-bench-20261123/Qwen3.5-4B-Q4_K_M.gguf
HF_HOME=/home/elicer/codex-bench-20261123/payload/hf-cache
```

고정 토크나이저 스냅샷도 `HF_HOME`에 있어야 합니다. 이번 검증에서는 기존에 검증한 해당 리비전의 파일을 인스턴스로 전달했습니다. 측정 당시 팀 웹서비스의 5173/8000 포트는 실행 중이 아니었으므로 팀 서비스의 전체 연결 완료를 주장하지 않습니다. GPU 연결 설정은 팀 백엔드 배포 시 적용해야 합니다.

검증 종료 시 GPU 설명 서버를 인스턴스 내부 `127.0.0.1:18091`에 실행해 두었습니다. 새 세션에서 건강 상태 HTTP 200을 확인했고, 인증 없는 completion 요청은 HTTP 401로 차단됩니다. 실제 연결 값은 `/home/elicer/codex-bench-20261123/service.env`에 권한 600으로 저장했으며 API 키 값은 Git에 포함하지 않습니다. 인스턴스를 다시 실행한 경우 위 서버 실행 명령도 다시 수행해야 합니다.

`benchmark_elice_explanations.py`는 전용 폴더의 검증된 `payload`를 사용합니다. 첫 실행은 `--repeats 1`, 기존 결과에 이어 실행할 때는 `--resume --repeats 1`을 지정합니다. 결과가 있으면 임의로 덮어쓰지 않습니다. 비공개 `results`에는 원시 시간·검사 결과·서버 로그를 보존하며, SSH 키·SMTP 비밀번호·모델 서버 API 키는 결과에 포함하지 않습니다.
